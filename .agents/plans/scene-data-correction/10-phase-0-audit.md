# Phase 0 audit: inventory and feasibility

Status: **primary-reviewed source audit; not an approved architecture contract**. Findings below distinguish verified repository/runtime evidence from unresolved feasibility and unverified causes.

This is a source and dependency audit of the current checkout. References are repository-relative unless explicitly marked as the cached SceneDB dependency or a runtime log. A source path establishes that code is wired or declared; it does not prove the path ran in the reported editor session.

## 1. Component registration, storage, and mutation producers

- Registered component classes are declared through `#[register_world_component]`; the derive emits inventory entries with a concrete `ComponentId`, JSON hydrate/remove callbacks, reflected getters/setters, and an optional GPU-mirror refresh callback. See `crates/core/pulsar_world_registry/src/lib.rs::WorldComponentRegistration` and `crates/core/engine_class_derive/src/lib.rs::register_world_component`.
- The runtime component declarations found in the Helio component crate cover static mesh, material override, light, camera post-process, global/local fog, portal, LOD, foliage, spline, four voxel component types, water volume, reflection capture, and post-process volume. Physics declares rigidbody and physics components; `pulsar_class` declares `ClassInstance` and `NativeScriptComponent`. See `crates/renderer/helio/crates/helio-component/src/components/**`, `crates/subsystems/pulsar_physics/src/components/{rigidbody_component,physics_component}/runtime.rs`, and `crates/core/pulsar_class/src/{component,native_script}.rs`. This is a source scan of macro declarations, not a runtime inventory dump.
- SceneDB stores these as ordinary typed ECS columns in `World`; the registry maps names to type-specific callbacks rather than storing an erased component value in a generic component-instance table. SceneDB's `World::insert<T>` and `World::get_mut<T>` are typed (`SceneDB` checkout `crates/pulsar_scenedb/src/world.rs::insert`, `get_mut`).
- Editor mutation has multiple entry points, not one command funnel. `SceneCommand::AddComponent` is one path (`crates/editor/ui_level_editor/src/core/commands/{types,executor}.rs`); attach/remove/enable/duplicate/reorder/nesting and edits also live in `crates/editor/ui_level_editor/src/core/scene_edit/components.rs`, and viewport asset drop has its own producer. The `AddComponent` command payload is JSON (`types.rs`); component-edit paths call `sync_registered_component_props_to_scene_db` at several sites (`components.rs`). This is a starting inventory, not proof that every UI producer is covered.
- Property writes can mutate an already-hydrated typed `EngineClass` through `WorldComponentRegistration::get_as_engine_class_mut`; `components.rs::update_live_component_property` then explicitly calls `refresh_world_component_gpu_mirror_for_class` (`crates/editor/ui_level_editor/src/core/scene_edit/components.rs`, `crates/core/pulsar_world_registry/src/lib.rs`).
- Script property setters also call the registration's GPU refresh callback (`crates/core/pulsar_world_registry/src/script_natives.rs`, setter paths around lines 133 and 201). The mesh custom hydrate loads asset geometry before inserting `StaticMeshComponent` (`crates/renderer/helio/crates/helio-component/src/components/static_mesh_component.rs::hydrate_static_mesh_component`).
- Runtime level hydration reads authored component data and dispatches registry hydrate callbacks (`crates/core/engine_backend/src/scene/runtime_level.rs::hydrate_components`). The callback contract is still JSON-shaped, even though storage after successful hydrate is typed.
- `PendingWorldWrites` is declared with `push` and `drain_and_apply` in `crates/renderer/helio/crates/helio-component/src/subsystems.rs`. Production producers found: camera post-process, global/local fog, foliage, water volume, reflection capture, post-process volume, and portal component runtime behaviors. The production source scan found no caller of `drain_and_apply`; verify against the whole linked runtime before removing or replacing it.
- One SceneDB entity can hold only one value of a given Rust component type; repeated `World::insert<T>` updates that typed column. Multiple same-type component instances therefore need distinct entities or another representation. SceneDB exposes ordinary entity spawn/despawn, but no component-instance entity/owner/multiplicity abstraction was found (`World::spawn`, `insert<T>` in the pinned checkout).

## 2. Notification and change consumers

- Renderer drains `world.take_component_change_events()` while synchronizing the scene (`crates/core/engine_backend/src/subsystems/render/helio_renderer/renderer.rs`, around line 804), then selects mesh/light related IDs for CPU row updates.
- The properties panel drains the same queue through `take_world_component_events` (`crates/editor/ui_level_editor/src/ui/properties/object_type_fields/mod.rs`, around lines 471–486; forwarding function in `crates/editor/ui_level_editor/src/core/scene_edit/components.rs::take_world_component_events`). Its source comment explicitly describes a single-drainer contract.
- Script object model drains that queue too and filters after taking it (`crates/core/pulsar_script_object_model/src/subscribe.rs::take_change_events_for`). Thus the queue is shared and destructive across at least three consumers; a consumer can remove notifications before another consumer reads them. This is a code-level race/ownership hazard; the audit did not reproduce a lost update in the running editor.
- SceneDB also exposes independent per-component cursors: `World::open_change_cursor<T>` and `World::read_changes` (`SceneDB` checkout `crates/pulsar_scenedb/src/world.rs`, around lines 356–385). The script driver uses them for `ClassInstance` (`crates/core/pulsar_game/src/scripting/driver.rs`, around lines 930–938). Journal overflow reports `ChangeRead::Overflowed`, requiring a rescan. This is evidence for independent readers, but its semantics and coverage for the editor's required property notifications still need validation.
- Preserve actual gameplay/event streams as a separate concern. This audit only establishes the shared SceneDB change queue and journal paths; it does not inventory every gameplay event channel.

## 3. Current GPU mirror and render-data path

- SceneDB's `#[derive(SceneStore)]` GPU support registers GPU-mirror callbacks, and World insert/mutation hooks dispatch writes when a mirror is attached (`SceneDB` checkout `crates/pulsar_scenedb/src/gpu/world_mirror.rs::GpuMirrorRegistration`, `world.rs::insert_inner`, `get_mut`, `attach_gpu_mirror`). `World::attach_gpu_mirror` does not replay existing rows; its documentation says rows inserted before their buffers are registered are not retroactively mirrored and must be inserted again. `SceneGpuStore::read_dirty_tracked_row_bytes` exposes CPU shadow bytes; upload is explicit via `World::flush_gpu_mirror`.
- The editor renderer still has CPU projection helpers. `crates/core/engine_backend/src/scene/helio_bridge.rs::sync_static_mesh_rows` reads authored mesh, transform, visibility, bounds, and movability; it creates/updates `helio_pass_gbuffer::StaticObjectComponent` and `MaterialComponent` rows, plus an `EditorMeshRow` marker. `project_movability` writes a separate Helio movability value. `mark_render_components_changed` forces component mutations to trigger the subscribed path. `ensure_gpu_mirror` manually registers buffers and re-inserts a selected set of existing components to seed the mirror.
- Light rows are also projected: `crates/core/engine_backend/src/scene/editor_rows.rs::sync_editor_light_rows` reads authored light/transform/visibility, writes the pass `LightComponent` and a billboard row, and projects movability.
- Runtime frame callers remain in `crates/core/pulsar_game/src/windowed_app.rs` (light and mesh synchronization around lines 696–697) and `crates/core/pulsar_game/src/embed.rs` (mesh sync around line 425). Editor and runtime therefore share these bridge helpers today.
- A mesh draw requires more than authored mesh geometry: the object batch consumes the `static_objects` buffer and computes draw counts (`crates/renderer/helio/crates/passes/3d/helio-pass-object-batch/src/lib.rs`); G-buffer checks draw count and binds `builtin_mesh_vertex`/`builtin_mesh_index` (`crates/renderer/helio/crates/passes/3d/helio-pass-gbuffer/src/lib.rs`). The static mesh component supplies the latter asset buffers, while the CPU bridge currently supplies `StaticObjectComponent`. A successful asset load alone does not establish a draw row or visible frame.
- `ObjectMovability` is projected into Helio movability and mesh flags by the bridge (`helio_bridge.rs::project_movability`, `object_row_flags`; `editor_rows.rs`). Its effect on visibility is **unverified**. The audit does not establish movability as the cause of missing meshes.
- Component runtime behaviors may separately enqueue typed writes into `PendingWorldWrites`; listed component families are not proven to reach a consumer. Other specialized GPU or simulation paths must be classified by source and sink before treating them as ordinary render-row projection.

## 4. Concrete pass dependencies and graph ownership feasibility

- Root-workspace `cargo metadata --no-deps` reports direct `helio-pass-*` dependencies only for `engine_backend`; its manifest lists billboard, decal, forward-lit, G-buffer, post-process, sky, TSR, voxel-planet, and water-sim. Concrete imports and pass component queries occur in `crates/core/engine_backend/src/scene/{helio_bridge,editor_rows,editor_postprocess}.rs`, `crates/core/engine_backend/src/subsystems/render/helio_renderer/{renderer,voxel_backend}.rs`, and tests `crates/core/engine_backend/tests/{voxel_block_api,editor_bloom_toggle}.rs`.
- Helio-workspace `cargo metadata --no-deps` lists direct pass dependencies in `helio`, `helio-core`, `helio-asset-compat`, `helio-default-graphs`, `helio-wasm`, `helio-web-demos`, `helio-snapshot`, and `examples` (in addition to pass-to-pass dependencies). `helio-component` is excluded from that workspace metadata. Concrete component/pass imports also occur in `crates/renderer/helio/crates/helio-component/src/components/**`; these include authored component hydrate/remove or mapping code that names pass-owned component types.
- The Helio facade itself directly depends on and re-exports pass types (`crates/renderer/helio/crates/helio/Cargo.toml`, `src/lib.rs`). `helio-core` also directly depends on foliage-place and Hi-Z pass crates (manifest). `helio-asset-compat` depends on forward-lit and G-buffer pass crates (manifest). These are separate boundary violations to inventory/migrate, beyond engine_backend.
- `helio-default-graphs` directly depends on many pass crates **and** on `helio` (`crates/renderer/helio/crates/helio-default-graphs/Cargo.toml`). This forms the current one-way edge `helio-default-graphs -> helio -> pass crates`; engine_backend depends on both `helio` and `helio-default-graphs`. The inspected manifests show no direct dependency cycle today. However, `helio-default-graphs` cannot yet be the only crate with pass dependencies while it depends on a facade that also names/re-exports passes. Feasibility requires removing/splitting pass dependencies and pass-named APIs from the facade/core/component/compat clients or revising the graph boundary. Whether that is practical without API redesign is unverified.
- Pass-owning crates also have pass-to-pass dependencies: `helio-pass-gbuffer` depends on shadow-matrix/radiance-cascades, and `helio-pass-object-batch` depends on G-buffer. The current strict proposal forbids these too; move shared contracts/helpers into neutral crates and let the graph connect pass inputs/outputs. The remaining edges still need a complete manifest ledger.
- `crates/renderer/helio/scripts/core-boundary` contains a boundary checker, but its current forbidden-dependency set and coverage against the proposed sole-owner rule were not executed or audited exhaustively.

## 5. Pinned SceneDB capabilities and gaps

The local dependency source used by the current manifests is SceneDB revision `e74df984b95ffe5235a67653a5b95a07e579df47` (cached at `C:/Users/redst/.cargo/git/checkouts/scenedb-17263c3373980689/e74df98/crates/pulsar_scenedb`).

- **Typed insert/mutate:** `World::insert<T: Component>` and `World::get_mut<T>` provide typed operations and mutation hooks (`src/world.rs`). `ComponentRef`/`ComponentHandle` can identify a registered component and expose erased reads/mutable access (`src/component_ref.rs`), but the public World insert API is generic over concrete `T`; no generic `Box<dyn Any>`/reflection-value insert was found. The registry has per-type callback dispatch and EngineClass access but its add/hydrate callback accepts `serde_json::Value` (`crates/core/pulsar_world_registry/src/lib.rs::WorldComponentRegistration`).
- **Component-instance entities:** `spawn`/`despawn` plus typed columns are available. No built-in owner-link, component-instance multiplicity, or attached-component model was found. Separate entities can be composed by the host, but identity/lifecycle semantics remain a host contract.
- **GPU mirror attachment:** insert/mutate hooks, GPU registration inventory, dirty upload, and CPU shadow reads exist. Late `attach_gpu_mirror` does not scan/replay existing World rows; the explicit `ensure_gpu_mirror` host helper compensates by hard-coded registration/reinsert code. Generic late attachment and buffer-capacity reconciliation are not provided by the observed API.
- **Independent notifications:** the per-component change journal supports independent cursors and overflow reporting; the legacy `take_component_change_events` queue remains destructive. Whether journal entries carry all property data needed by panels or only invalidation/change identity must be confirmed from `src/change_journal.rs` before selecting it as the UI contract.
- **Durable typed archive:** this audit did not find an archive API in the inspected SceneDB World/GPU surfaces. Persistence format and plugin type lifetime remain open; absence from these files is not proof no separate serialization crate exists.

## 7. Symptom evidence: verified facts versus hypotheses

- **User-reported symptom:** adding scene components, particularly meshes, in the level editor yields no visible mesh; user also reports the issue is broader than meshes. This is a report, not an independently reproduced result in this audit.
- **Runtime log fact:** `C:/Users/redst/AppData/Roaming/Pulsar/Pulsar_Engine/data/logs/2026-10-04_19-39-57/engine.log` records repeated hydration failures for `LightComponent` on `object_3`: flat floating-point `1002.0` was deserialized where nested `IntensityLightProps` was expected (lines 135–153). This establishes a light hydration/schema error in that run; it does not establish the mesh failure's cause.
- **Runtime log fact:** the same log records loading `SM_Cube.fbx` and 24 vertices/36 indices by `StaticMeshComponent` (lines 3390–3394, with later repeated loads). This establishes that the asset loader produced geometry; it does not establish a SceneDB GPU row, object-batch draw count, pass execution, or visible pixels.
- **Source fact:** renderer/editor/script have competing destructive drains, CPU mesh/light projection remains wired, some runtime behaviors enqueue writes with no production drain found, and GPU mirror late attach does not replay rows. Each is a verified architecture risk above. None has been proven as the unique cause of the reported image.
- **Unverified hypotheses:** movability classification could affect shadow partitioning but no evidence here shows it hides the main mesh; missed change delivery could leave a projection stale but no lost notification was reproduced; hydration shape mismatch demonstrably affects light, not necessarily mesh; current logs do not contain a verified draw count, GPU row dump, pass trace, or screenshot comparison. An end-to-end reproduction must capture those values before assigning root cause.

## Audit limits and next evidence needed

This audit records a source-level inventory, not an architecture decision. The component declaration list is a macro/source scan, not a runtime dump from the launched binary. Pass dependency lists come from root/Helio workspace metadata and source search, not every transitive feature/target combination; the Helio component package is excluded from its metadata. Runtime evidence is limited to the named log. No live reproduction, GPU readback, rendered-frame capture, or test/build target ran. Earlier workaround edits in the editor command executor and viewport asset handler are present in the working tree; they arm subscriptions/refresh render rows and do not validate the architecture. Phase 0 still needs a linked registration inventory, full journal payload semantics, a valid `helio_component` test workspace and an end-to-end capture of one failed add through component identity, GPU row bytes/generations, batch draw count, pass execution, and frame output.
