stable `scenedb_dylib` name) was merged with `origin/main` (the r3

## How the conflicts were resolved

- **gi** (`GiResolvePass`, `GiIntegratePass`): the local side made GI's
  pipelines `DeferredCompute` so they compile in the build's batch; the remote
  added the pixel gather (`ResolveGather`, a second pipeline in the resolve).
  Kept `DeferredCompute` for every pipeline, including the gather's, so the
  resolve's match arms have one type. The remote's new `cache.rs` and
  `gather.rs` built eagerly; they now use `create_compute_pipeline_deferred`
  and `DeferredCompute` too (the `compute` helper returns it).
- **sky**: the remote's radiance table (`sky_radiance_kernel`, the irradiance
  table is its integral) was written against `params_only: bool`; the local
  side replaced that flag with the GPU plan (`SkyPlan`, `gate: Option<slot>`).
  The radiance kernel is a new plan slot (`SKY_PLAN_SKY_RADIANCE = 3`, the
  planet weather moves to slot 4 and its slice to `groups[5]`); `SkyPlan::args`
  (WGSL), `ResolveUniform::groups`, `plan_groups` and `resolve`'s loops grow by
  one. The radiance output took group 1 binding 8, which the local plan buffer
  used (a module-wide binding collision in WGSL): the plan buffer moved to
  binding 10 (the layout and the shader).
- **voxel** (`chunks/rays.rs`): the local side batched the whole ray-kernel set
  through the side-by-side helper when a stream is first traced; the remote
  replaced `RayPipelines` by one job per `RayKernel`, started only for the
  kernels a scheduled stream needs, in the order it needs them. Took the remote
  file: its jobs already compile off the frame in parallel and compile less.
  The chunk and draw bundles in `volumes.rs` keep the side-by-side helper.
- **workspace_hack**: `pulsar_scenedb` and `pulsar_scenedb_derive` stay path
  dependencies into the submodule (with the `telemetry` feature the workspace
  enables), the remote's git-rev lines are dropped. `cargo hakari` is not
  installed here, so the file was merged by hand; the remote's new entries
  (`helio-pass-denoise`, `helio-pass-history`) came through git.
- **Cargo.lock**: git's merge left `scenedb_dylib` at 0.1.0 while the merged
  SceneDB is 0.1.1, which made cargo re-resolve unrelated crates (phf 0.10,
  windows 0.54: a `windows` mismatch that broke `wgpu-hal`). The lock now
  names 0.1.1 and `--locked` passes; nothing else changed.

## Fixes the merge needed outside the conflicts

- **water** `tests/scene_rows.rs`: a static mesh's `indices` are `Arc<[u32]>`
  since meshes shared geometry per asset (already broken before the merge).
- **scenedb**: `gpu_texture_staged` is gated on the `gpu` feature like
  `gpu_texture_mips` (the remote's fix for the same problem).
- **gi** `tests/pixel_gather.rs`: the near-field test read the texture on the
  first frame that had one. With the local asset pump the room's geometry binds
  over several frames, so it read an empty frame (every factor 1). It waits for
  lit pixels now (as `settle` does). Passes on the remote alone, fails without
  this on the merged tree.

## SceneDB revs in Helio

Helio's `Cargo.toml` (two crates), `crates/helio_dylib/Cargo.toml` and its
`Cargo.lock` name SceneDB by git rev. The documented rule is that they equal the
submodule's commit, but a rev that is not on GitHub yet makes cargo fail to
resolve (the `[patch]` still needs the git source's revision), so they stay on
the last pushed rev (`f958912`). After SceneDB is pushed, bump all three files
to its merge commit (a Helio commit, then re-pin).
