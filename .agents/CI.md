# CI

| Workflow | When | What |
|---|---|---|
| `ci.yml` | PR (non-draft), push to `main`, nightly, manual | fmt (Pulsar-Native's own crates, `scripts/fmt-check.sh`), workflow lint, clippy + guards + nextest on **Linux**, packaging smoke test, pin checks |
| `ci.yml` (`cross-platform`, smoke on macOS/Windows) | `main`, nightly, `gh workflow run CI -f full=true` | Windows/macOS compile check and packaging smoke test; never per PR |
| `security.yml` | PRs touching manifests; weekly | dependency review (needs the repo's Dependency graph enabled), `cargo audit` |
| `release.yml` | push to `main` with a version bump | full release gate and builds |
| `pr-release-guard.yml` | PR | blocks `[FORCE-RELEASE]` commits |
| `plugin-release.yml` | called by each plugin repo's `release.yml` (push to its `main` with a version bump, or manual) | builds the plugin root with `--features dll` for linux x86_64, windows x86_64/i686/arm64 and macos x86_64/arm64 and attaches the libraries and `sdk-versions.json` to the tag `v<version>`; written once here, called from all 34 plugin repositories |

Cost rules: branch pushes do not run CI (the PR does); a new push cancels the
superseded PR run; docs-only changes and draft PRs skip CI; tests run on Linux
only; Windows/macOS minutes are spent on `main` and nightly. Tests that need a
GPU are excluded by `.config/nextest.toml` (`ci` profile). Run a full
cross-platform pass on a branch with `gh workflow run CI --ref <branch> -f full=true`.

The Linux lane also runs `cargo run -p todo_check`. It scans Git-tracked
source and configuration files in this repository (not submodules) for TODO
comment markers without an issue reference, such as `#123` or a GitHub issue
URL. Existing unreferenced TODOs are reported too; they must be linked to
issues before this check can pass.

## Shared library releases

The shared UI, reflection, profiling, SceneDB and renderer libraries (`.agents/PLUGIN_SYSTEM.md`, "Shared
libraries") are released from the repository that owns each. Each repository's `sdk-release.yml` is a short
caller of one reusable workflow here, `.github/workflows/library-release.yml`: on a version bump of its `*_dylib`
crate it builds six platforms and publishes, under the tag `shared-v<version>` (its own series, so the
repository's other releases never count as it):

- the library and, on Windows, its import library;
- `<package>-<platform>-sdk.tar.gz`: a Cargo SDK, the crates inside the library already compiled
  ([Cargo-SDK](https://github.com/Far-Beyond-Pulsar/Cargo-SDK), `cargo sdk`);
- `<package>-<platform>-manifest.json`: toolchain, source and the hash of `Cargo.lock` it was built with.

The SDK is cut from `sdk_roots` (`tools/sdk_roots`), the package that depends on all six libraries and on the
feature pin, so one build covers the chain. Helio sits on top of it: Helio's SDK holds every crate of the six.

Plugin and engine builds fetch that SDK (`cargo sdk fetch`) and run `cargo build` under `cargo sdk exec`, so the
crates inside the libraries are served, not compiled. A plugin release first checks that every library has a
release (a different `Cargo.lock` only warns: the SDK then serves fewer crates, the build stays correct); the engine release falls back to compiling everything, with a
warning, when no SDK exists yet. The libraries release first, then the plugins and the engine.

What makes the SDK match: Cargo derives a crate's file name hash from its source, features, dependencies, profile,
target, flags and compiler. Builds of one workspace give a crate different features depending on what else is in
the build, and under resolver 2 the copy a build script or proc-macro uses is unified apart from the copy the
target code uses. `tools/workspace_hack` (generated by `cargo run -p hack_gen`, checked with `--check`) lists
every crate inside the libraries with the union of its features, as a dependency and as a build dependency, per
platform; the engine, every plugin build and `sdk_roots` include it, so every build resolves the same hashes.
Regenerate it whenever a dependency of a library or plugin changes.

Measured (Windows x86_64, one plugin, empty target directory): 640 s without an SDK, 222 s with one
(`docs/benchmarks.md` in Cargo-SDK). The SDK of a platform is about 1 GB compressed; a release asset is limited
to 2 GiB, and the workflow fails above that.

The shared-library mechanism is verified on windows x86_64 only: the other five platforms' cargo config
(`prefer-dynamic`, rpath) and the native-library exports are untested until their runners pass.
